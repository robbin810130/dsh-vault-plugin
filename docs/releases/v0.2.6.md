# Vault v0.2.6 — reliability and privacy hardening

Target combination: DSH **0.1.5-rc.1**, official source commit
`183f08e9c6dde7e36cd2318eaee70b0da08fb35e`, with this release's matching host patch.
Installing the plugin alone does not apply that patch. Do not apply it to a different DSH version.

## Changes

- Password policy uses a validated draft and explicit **保存策略** action, serialized writes, leaf-level merging and conflict feedback. Clearing an input no longer silently writes a weaker policy. Multi-field host settings writes are not transactional; failures explicitly warn that some fields may already have saved. This client-side merge is not cross-browser atomic compare-and-swap.
- Recovery-key delivery is memory-only and independent of workspace/session row lifecycle. A valid successful response still delivers the key when its snapshot is older than the current snapshot. Protection takes effect immediately; a persistent overlay requires acknowledgement. Refreshing or closing the page still loses the one-time key; the UI warns about this.
- Quick-lock groups use neutral aliases. Locked group names are concealed in settings text and accessible labels; existing data is not renamed.
- Unknown/offline protection state fails closed. Matching host seams carry authoritative workspace context into session rows, search and the central unlock action, including children of collapsed workspaces.
- Unlock, password-change and recovery share bounded, per-group serialized verification. Lock operations revoke admitted credential work before it can leave a usable grant. Limits apply per service instance, not across independent servers.
- State locks publish complete owner metadata atomically. Only confirmed-dead local owners are eligible for automatic recovery. Empty, damaged, foreign-host, PID-reused, or ambiguous locks require stopped-service operator recovery; age alone never permits deletion.
- Interrupted state commits retain a durable rollback record so recovery can restore the original primary and backup generations. An error after removing the undo record may have an indeterminate commit outcome: re-read before retrying. This does not make state and audit writes a crash-atomic transaction.
- Release tags now require matching package versions and release notes, plugin tests, both plugin typechecks, and packaging/installer tests.

## Upgrade and recovery

Back up the installed plugin, matching host bundles, profile configuration and Vault state before replacing files. Stop the DSH service before deployment, then restart exactly one instance and verify installed hashes and a read-only snapshot. Preserve existing password policy and protection bindings.

The state directory is the explicit configured override, `DSH_VAULT_STATE_DIR`, `$DSH_HOME/vault-lock`, or `~/.dsh/vault-lock`, in that precedence order. Never delete an unknown lock while a writer might still be active. Keep recovery artifacts for diagnosis; reaper tombstones intentionally persist to prevent delayed reclaimers deleting a replacement lock.

## Security and validation boundaries

This is a **foreground privacy lock**, not content encryption or server-side authorization for DSH content APIs. Group metadata and bindings remain plaintext; passwords and recovery keys use scrypt verifiers. Manual locking remains scoped to the current client identity.

The release workflow runs plugin tests and plugin host/client TypeScript checks. It does not certify a clean full DSH typecheck or cross-platform runtime behavior. Pinned host tests and local browser/deployment results are documented separately in the compatibility and delivery records.

Deferred: emergency CLI streaming-input repair (F09), portable doctor/installer/rollback automation, full cross-tab and sleep/wake semantics, and exhaustive subagent/right-sidebar/streaming privacy coverage. The historical 0.1.2 patch is retained as a historical asset, not a claim of fresh 0.2.6 runtime validation on that version.
